Tokenization · Test-time training

How I got highlighted by OpenAI in their pretraining competition

CaseOps, phased test-time training, and making the most of 16 MB.

Romeer Pillay·May 20, 2026·6 min read
On this page

  2. CaseOps

OpenAI highlighted my CaseOps tokenizer in its Parameter Golf write-up, in the section on new modeling and data ideas. The idea was small: stop making a tiny language model learn separate vocabulary for the same word in different cases.

The other contribution I want to talk about is phased test-time training. It lets the model carry something useful from one evaluation document into the next.

These were the two most interesting things I contributed to the competition. One changes how text is represented. The other changes when the model gets to learn.

A language model in 16 MB#

Parameter Golf asked us to train the best language model we could fit into a 16 MB artifact, including the counted code and compressed weights. Training had to finish within ten minutes on eight H100s. Evaluation got its own ten-minute budget.

The score was bits per byte on held-out FineWeb text. Lower is better: how many bits does the model need, on average, to encode a byte of the original text?

That makes tokenization unusually interesting. You can change the vocabulary or the representation, but you still pay for predicting the same original text. Under a small memory budget, the question becomes how much of the model's capacity is going toward useful distinctions.

CaseOps#

Consider these:

apple
Apple
APPLE

They share almost all their structure. A conventional case-sensitive vocabulary can spend separate entries on those variants, or break them into different subword sequences. Either way, capitalization gets tangled up with the lexical representation.

CaseOps separates the two. The lexical stream is lowercase; a small set of operators preserves the casing.

apple  → apple
Apple  → [TITLE]apple
APPLE  → [ALLCAPS]apple

Now the tokenizer can reuse the same lowercase pieces, while the model learns a reusable capitalization operation.

This is a reversible transform before SentencePiece BPE. The representation still contains every capital letter. The model has to predict the operators too.

Four small operators#

The implementation works over runs of ASCII letters:

  • TITLE capitalizes the first letter of a run.
  • ALLCAPS capitalizes the whole run.
  • CAPNEXT capitalizes the next letter, for mixed-case words.
  • ESC escapes a literal control character.

Lowercase runs pass through unchanged. Non-ASCII characters also pass through unchanged. The operators are reserved characters in the actual transform; the names below make them readable.

Mixed case makes the benefit a little less tidy. A name like OpenAI needs multiple operations. But title case and all-caps words have short descriptions, and the transform gives us those descriptions directly.

The useful bias is that spelling and casing can share structure. Learning what “apple” means no longer has to be completely separate from learning how to capitalize it. With only 8,192 vocabulary entries, that is an appealing place to save duplication.

Counting the original bytes#

There is one important bookkeeping detail. The transformed stream has a different byte length, so scoring against its bytes would change the task.

The exporter writes a byte-count sidecar alongside the validation tokens. The evaluator uses those counts to charge the prediction loss against the original UTF-8 bytes. Capitalization operators still cost prediction bits; inserting them doesn't inflate the denominator.

The exporter and record README have the transform, reserved-symbol configuration, and byte-accounting details.

My CaseOps submission finished at 1.06780 BPB averaged over three seeds, in about 15.94 MB. It combined the tokenizer with a mild late weight-decay taper on the existing phased-TTT stack. That number belongs to the whole submission.

What I like about CaseOps is how little machinery it needs. The transformer stays a transformer. We just give it a representation with less duplicated structure to learn.

Phased test-time training#

The competition allowed a useful form of online learning: once a token had been scored, the model could train on it to help predict future tokens. Its original score stayed fixed.

Earlier work by samacqua already used this inside each document. Score a chunk, update a LoRA adapter using that chunk, then predict the next one. At the document boundary, reset the adapter.

That gives the model a short-lived memory of the current document. My addition was to let the shared base model learn across documents as well.

Two timescales#

Document-local adaptation is good at picking up the topic, terminology, and style of the text you're currently reading. But resetting the adapter throws that adaptation away.

The base model offers a second place to put learning. It can absorb changes from already-scored documents and pass them on to later ones. Local LoRA still handles the specifics of each new document.

My first phased implementation kept the existing evaluator and inserted one pause:

  1. Score documents using the usual per-document LoRA adaptation.
  2. After 2,000 documents have completed in the evaluation queue, gather those documents.
  3. Run distributed SGD on that already-scored prefix to update the base model.
  4. Resume the queue with the updated base and fresh local adapters for subsequent documents.

The ordering is the whole trick. The global update only sees documents whose scores are already counted. It improves the starting point for later predictions without going back and changing earlier scores.

Why phases#

I initially tried a more continuous combination of local and global updates. It was harder to make that run efficiently across GPUs: synchronizing the shared base model kept getting in the way of the local work.

A phase boundary makes that coordination much simpler. The GPUs finish a defined amount of scoring, do a shared training job, then return to scoring. It also makes the information flow easy to follow: everything entering global SGD has already been evaluated.

The original record left training unchanged and moved the three-seed mean from 1.07336388 to 1.07280628 BPB, with evaluation taking about 507 seconds on average. A small improvement, with an extra learning mechanism that others could build on.

And they did. dexhunter's next version extended the idea to three phases, alternating scoring and global SGD several times. That was the stack I later built the CaseOps submission on.

I like that loop: contribute an idea, someone improves it, then their improvement becomes the starting point for your next experiment.

Sharing what can be shared#

CaseOps and phased TTT solve different problems, but both make better use of shared structure.

CaseOps shares lexical pieces across capitalization patterns. Phased TTT shares learning across documents while preserving a separate, fast adaptation path for each one.

The constraints made both ideas worth trying. With a much larger model or a much longer run, it is easy to leave a bit of duplication or unused learning on the table. Sixteen megabytes and a ten-minute clock make you notice it.

And sometimes a few capitalization operators are enough to get your tokenizer into OpenAI's write-up.
