Reverse engineering DiMuon through a training API

Turning a language-model API into a matrix test bench, finding the update rule, and getting sidetracked by floating point.

Romeer Pillay·October 28, 2026·9 min read

A language-model API is a strange place to reverse engineer a matrix optimizer. You can't hand it a matrix. You hand it tokens and a loss, then look at how the weights moved.

Thinking Machines added DiMuon to Tinker with a learning rate, momentum and gradient clipping, but no update equations. I wanted to see how much of it we could work out from the outside.

The answer turned out to have a nice shape: scale the momentum's rows and columns, apply a polar transform, apply the same scaling again, then set the update's length.

We built a local version that reproduced four steps of real SST2 gradients, down to every recovered FP16 value in the polar output. Getting there involved turning LoRA into a little linear algebra lab—and then spending far too long arguing with floating point.

Part 1 / The optimizer

A small, trainable detour#

LoRA keeps the original model weight fixed and learns a change through two smaller matrices, A and B. A squeezes the input into a few coordinates; B expands it back out. The number of coordinates is the adapter's rank.

The effective weight is W₀ + sBA, where s is a scale factor. That skinny detour is all the optimizer gets to change.

Muon takes a momentum matrix and approximately makes its nonzero singular values equal. Instead of letting one large direction dominate, it spreads the update across the available directions. A short matrix-polynomial iteration approximates this polar transform.

Applying ordinary Muon to A and B was our starting guess. But the version we tried gave the tall B factor a much larger step than A. DiMuon gave both factors the same update norm. Even after rescaling our Muon predictions, the directions were still off by about 20% at the median.

There was more going on than a different learning rate.

Making the API answer small questions#

First, we needed a gradient meter. The idea came from Martin Marek's StableReinforce thread: use a carefully chosen Adam step to read gradients from downloaded weights.

With both Adam betas set to zero, a large epsilon makes the update almost linear in the gradient. The exact equation is invertible. Adam becomes a measuring instrument.

The gradient-meter equations

With no clipping or weight decay, a coordinate moves by:

u=−ηg∣g∣+ϵ,g=−ϵuη−∣u∣.u=-\eta\frac{g}{|g|+\epsilon}, \qquad g=-\frac{\epsilon u}{\eta-|u|}.u=−η∣g∣+ϵg​,g=−η−∣u∣ϵu​.

Large epsilon avoids saturation. We repeated measurements with different epsilon values to check the recovered gradients, including their rounding.

Then LoRA gave us a convenient way to simplify the model. At initialization, B is zero. The gradient of A is therefore zero too. If the adapter is on the output projection, the transformer supplies a fixed feature h, and the trainable part is just sBAh. From B's point of view, the language model is a linear system.

We used signed token weights that sum to zero. This cancels cross-entropy's shared log-sum-exp term, leaving a linear combination of logits. Combining calibrated contexts gave us useful matrix patterns inside that linear system.

The best experiments made most of the optimizer irrelevant:

  • Change history without changing weights. Take steps with learning rate zero. Then set beta to zero on the measured step. Ordinary momentum forgets the history—but DiMuon still responds to it.
  • Cancel signed history. Make old gradients oppose each other. The scaling follows the old signed momentum, rather than an average of squared gradients.
  • Make the polar response cancel. Give it two equal axes, then compare their ratio after the update.

That last one is my favorite.

We didn't need an exact polar implementation to identify the scaling after it. Symmetry had removed that unknown from the experiment.

The sandwich#

Here's the rule we arrived at. The current gradient feeds an ordinary momentum EMA. The previous momentum supplies row and column statistics. Those statistics scale the matrix both before and after the polar transform.

The final operation sets the update norm, so the taller LoRA factor doesn't automatically get a much bigger step.

The old momentum gives the optimizer a picture of which coordinates have been active. And it is already sitting in memory: the row and column scaling comes without keeping another moving average.

Rows and columns with more old momentum get smaller multipliers. The polar transform chooses a direction in those rescaled coordinates; applying the multipliers again maps that direction back. The last normalization chooses its length.

This is also a useful geometric interpretation: an ideal polar factor is a steepest-descent direction under an operator-norm constraint. The diagonal sandwich changes the geometry of that constraint. On LoRA's skinny matrices, collecting these row and column statistics is cheap.

This predicted a held-out rank-16 norm to about 5.6 × 10⁻⁸ relative error. The origin of 0.175 is still a mystery.

A LoRA wrinkle is that multiplying A by c and dividing B by c leaves BA unchanged. The optimizer still sees different factor coordinates. Equal-sized A and B updates don't automatically mean equal-sized changes to the effective model weight.

Part 2 / The numerics detour

Same equation, different answer#

Once the rule looked right, we wanted the numbers to line up. Close was less interesting than figuring out exactly why they differed.

Almost-canceling gradients exposed the momentum storage: the current calculation needed FP32, while the state carried into the next step behaved as BF16. Tiny coordinates exposed intermediate FP16 stores in the polar iteration. Those coordinates barely affected the total error, but their ratios made the rounding choice obvious.

Five stages of Polar Express v3, evaluated in Horner form, gave us the polar computation. Then the parentheses started to matter: algebraically equivalent expressions gave different answers once we rounded the intermediates.

The polar computation we replayed

Normalize the preconditioned momentum and store it in FP16:

X=round⁡FP16(DrMtDc1.01max⁡(∥DrMtDc∥F,10−7)).X=\operatorname{round}_{\mathrm{FP16}}\left( \frac{D_rM_tD_c}{1.01\max(\|D_rM_tD_c\|_F,10^{-7})} \right).X=roundFP16​(1.01max(∥Dr​Mt​Dc​∥F​,10−7)Dr​Mt​Dc​​).

For a tall matrix, form the small Gram matrix R = XᵀX and apply a stage:

X←X[aI+R(bI+cR)].X\leftarrow X\left[aI+R(bI+cR)\right].X←X[aI+R(bI+cR)].

The coefficients change each stage. Wide matrices use the transposed construction. The intermediate stores matter, as does how the GPU reduces each matrix product.

One SST2 update still had a 0.79% spectral direction error on CPU. Moving the same equations to an H100 brought that case to about 7.7 × 10⁻⁸. All 2,913 previously mismatched inferred FP16 output values matched.

The first Gram matrix had changed by one rounding step, and the polynomial amplified it. A tiny difference at the start of the computation had looked like a missing piece of the optimizer.

Even two GPU paths could disagree. A GPU can split a long dot product into chunks, compute the chunks separately, and add the results. Change the chunks and you change where rounding happens. Recreating that grouping let us reproduce two different answers from the same equation.

Checking the measuring instrument#

At one point, the gradient meter itself started giving different answers at the same weights.

The clue was another rounding choice: round each contribution before adding, or add the products and round once afterward. That small change explained more than 12 million gradient values exactly.

At B = 0, a single-example B gradient also gives us a peek inside the model. It is a rounded outer product between a backward signal and the projected activation Ah. Every rounded value supplies an interval constraint on that projection.

Change A's seed while keeping B zero, and you get a second instrument looking at the same effective model. This caught a hidden vector that passed the first probe and failed the second. Eight coordinates had missed a difference in a 4,096-dimensional vector.

Then one dot product landed almost exactly on a BF16 rounding boundary. Its inputs were binary floats, so we could calculate it exactly with integer arithmetic.

We had been looking for a model difference when part of the problem was how we were measuring it.

Even normalization joined in. rsqrt(x) and 1 / sqrt(x) are the same on paper, but gave us different rounded activations. One changed value was invisible to the first few probes, then showed up later as the model carried it through more layers. By this point, the project had become a fairly elaborate way to appreciate parentheses.

Putting the pieces back together#

Finally, we fed the reconstruction gradients from four batches of SST2 sentiment examples, using rank-one LoRA on Qwen3-8B's output projection. It carried its own momentum and weights from one update to the next. The gradients came from measurements at Tinker's weights.

Every recovered FP16 value in the polar output matched. After four steps, the largest difference in the accumulated weights was 9.3 × 10⁻¹⁰. Running it again on another H100 gave the same spectral matches.

Experiment and measurement details

The ordinary steps use learning rate 0.001. Subtracting two nearly equal exported weights loses precision, so we also measure updates with the learning rate enlarged to 16. That changes the readout gain while keeping the optimizer state and gradient fixed.

With that readout, relative update errors were 7.6 × 10⁻⁸ to 1.21 × 10⁻⁷. At the ordinary learning rate, errors in the subtracted updates range from roughly 2 × 10⁻⁶ to 2.4 × 10⁻⁵; the accumulated local weights differ from the hosted weights by at most 9.3 × 10⁻¹⁰. The replay uses measured gradients at the hosted weights; it does not recompute them with a separate local language model. Other experiments include an unresolved 0.81% discrepancy in a rank-two B continuation and 1.14% RMS across historical A updates. The data linked above covers the four-step rank-one experiment.

My favorite part was how much easier the problem became once we stopped asking the whole optimizer to explain itself at once.

A cold LoRA factor gave us a linear system. Zero learning rate let us change history without moving the weights. Equal axes made an unknown transform cancel. Tiny coordinates made rounding visible.

Each trick turned a big opaque system into one small question. Eventually, those answers added up to an optimizer.
