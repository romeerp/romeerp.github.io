Reverse engineering DiMuon through a training API

Taking apart a LoRA optimizer, one controlled gradient at a time. Then getting distracted by floating point.

Romeer Pillay·October 28, 2026·10 min read
On this page
  1. Part 1 Figuring out the optimizer
  2. Part 2 The numerics rabbit hole

Thinking Machines put a new LoRA optimizer called DiMuon into Tinker. The docs give you a learning rate, a momentum coefficient, and gradient clipping, but no update equations. It seemed like a fun thing to reverse engineer.

The rule we arrived at has a nice structure: take momentum, scale its rows and columns using the previous momentum, run a Muon-like polar transform, apply the same scaling again, then normalize the update.

The trick was persuading a hosted language model to give us simple gradients. Once we could do that, we could take the optimizer apart one piece at a time. Then we got distracted by floating point.

Part 1 Figuring out the optimizer#

A little LoRA background#

LoRA writes a weight change as the product of two small matrices:

Weff=W0+sBA,A∈Rr×din,B∈Rdout×r.W_{\mathrm{eff}} = W_0 + sBA, \qquad A\in\mathbb{R}^{r\times d_{\mathrm{in}}}, \quad B\in\mathbb{R}^{d_{\mathrm{out}}\times r}.Weff​=W0​+sBA,A∈Rr×din​,B∈Rdout​×r.

The original weight W₀ stays fixed. A compresses an input into r coordinates; B maps those coordinates back to the output dimension. The scalar s sets the adapter scale.

Muon takes a momentum-like matrix and approximately replaces its nonzero singular values with ones. This spreads the update across singular directions instead of letting the largest one dominate. In practice, it uses a short matrix-polynomial iteration to approximate that polar transform.

Our first guess was to apply an existing Muon implementation to each LoRA factor. A is wide and B is tall, so this immediately raises a question about how the two steps should be scaled.

The step sizes gave us our first clue. At rank eight, all 192 nonzero MLP factor updates had the same norm per unit learning rate to seven significant figures: 2.219139. With the Muon implementation we were using, the median was 2.575 for A and 85.397 for B. Its aspect-ratio scaling made a huge difference for the tall factor.

Changing the learning rate wouldn't fix that imbalance. Even giving each Muon update its own best-fitting scale left about 19.6% median directional error. Something was changing the direction too.

Turning the API into a test bench#

We could choose a hosted model, submit losses, take optimizer steps, and download checkpoints. We couldn't just hand the optimizer a matrix and ask what it would do. First we needed a way to measure gradients, then a way to make useful ones.

The starting trick came from Martin Marek’s StableReinforce thread. He recovered gradients from downloaded weights using large-epsilon Adam steps, and traced the objective to REINFORCE plus score centering. We borrowed his gradient meter.

Set both Adam betas to zero, turn off weight decay and clipping, and a single coordinate moves by:

u=−ηg∣g∣+ϵ.u=-\eta\frac{g}{|g|+\epsilon}.u=−η∣g∣+ϵg​.

You can invert that:

g=−ϵuη−∣u∣.g=-\frac{\epsilon u}{\eta-|u|}.g=−η−∣u∣ϵu​.

A large epsilon keeps this away from saturation. Measuring the same gradient with different epsilon settings gives us a useful cross-check. Adam is now a way to read gradients through an API that doesn't expose them.

The next trick is especially nice. LoRA starts with B = 0, which makes the gradient of A zero. Put the adapter on the output projection and the logits are:

logits(h)=fixed logits(h)+sBAh.\mathrm{logits}(h)=\mathrm{fixed\ logits}(h)+sBAh.logits(h)=fixed logits(h)+sBAh.

During this experiment, h is a fixed feature from the transformer. From B's point of view, the whole language model has become a linear system.

We used signed token weights that sum to zero. That cancels the shared log-sum-exp term in cross-entropy, leaving a linear combination of logits. Combining a few calibrated contexts lets us construct useful gradient directions and small matrix patterns inside this system.

We could also prepare simple adapter states without uploading edited weights. A zero-loss AdamW step halved A exactly while keeping B zero. Sign-like updates wrote a little B block with orthogonal, equal-norm columns. Save it, restore it into a DiMuon client, and we had a repeatable starting point.

The two factor gradients are linked:

GAA⊤=B⊤GB.G_AA^\top=B^\top G_B.GA​A⊤=B⊤GB​.

Within that constraint, we now had a little programmable test bench.

One moving part at a time#

The search got much easier once we started designing gradients that switched off most of the optimizer. Each experiment could then ask about one operation.

For example, we built up history with learning rate zero, so the weights stayed fixed. Then we set beta to zero for the measured step. Ordinary momentum now forgets the old gradient, but the DiMuon update still depended on the history.

History had another job. We arranged for old gradients to cancel and watched what happened to the scaling. It followed the previous signed momentum, rather than an average of squared gradients.

To test for scaling after the polar transform, we made two axes equal at its input. The spectral computation then treats them equally, and final normalization cancels their common gain. Whatever inequality remains in the output has to come from the surrounding machinery.

The post-scaling formula gave 1.999700097. The API gave 1.999700130. Making just one column active let us pull apart the row and column effects.

The nice part is that we could get this answer while our implementation of the spectral transform was still wrong. We had made that unknown irrelevant to the question.

The rule#

Putting those pieces together gives:

First, clip the gradients jointly if clipping is enabled, then do the usual momentum EMA:

Mt=βMt−1+(1−β)G~t.M_t=\beta M_{t-1}+(1-\beta)\widetilde G_t.Mt​=βMt−1​+(1−β)Gt​.

Use the previous momentum to compute row and column energies:

ei=∑jMt−1,ij2,fj=∑iMt−1,ij2.e_i=\sum_j M_{t-1,ij}^2, \qquad f_j=\sum_i M_{t-1,ij}^2.ei​=j∑​Mt−1,ij2​,fj​=i∑​Mt−1,ij2​.

Divide each energy vector by its own maximum and turn it into diagonal scaling matrices:

Dr=diag⁡ ⁣[(eimax⁡kek+10−4)−1/4],Dc=diag⁡ ⁣[(fjmax⁡kfk+10−4)−1/4].D_r=\operatorname{diag}\!\left[ \left(\frac{e_i}{\max_k e_k}+10^{-4}\right)^{-1/4} \right], \qquad D_c=\operatorname{diag}\!\left[ \left(\frac{f_j}{\max_k f_k}+10^{-4}\right)^{-1/4} \right].Dr​=diag[(maxk​ek​ei​​+10−4)−1/4],Dc​=diag[(maxk​fk​fj​​+10−4)−1/4].

If the whole old momentum is zero, the relative energies default to ones. The small ridge keeps inactive rows and columns from getting unbounded multipliers.

Then apply the sandwich and set the step size:

Ut=Dr Φ(DrMtDc) Dc,Δθt=−η C(r)Ut∥Ut∥F.U_t=D_r\,\Phi(D_rM_tD_c)\,D_c, \qquad \Delta\theta_t=-\eta\,C(r)\frac{U_t}{\|U_t\|_F}.Ut​=Dr​Φ(Dr​Mt​Dc​)Dc​,Δθt​=−ηC(r)∥Ut​∥F​Ut​​.

Here Φ is the approximate polar computation, including its input normalization, and C(r) is a rank-dependent update norm. A zero direction gets a zero update.

The fourth root looks a little odd until you remember that the energy is a squared norm. An inverse fourth root of energy is an inverse square root of the corresponding norm. So this is still fairly simple row-and-column normalization machinery.

The step norm had an odd little pattern. At alpha 32, our tested ranks from 1 through 64 followed:

C(r)=r(r32)0.175.C(r)=\sqrt r\left(\frac r{32}\right)^{0.175}.C(r)=r​(32r​)0.175.

This predicted the rank-16 norm to about 5.6 × 10⁻⁸ relative error before we queried it. We never figured out where the 0.175 comes from.

The geometry behind the rule#

There's a neat interpretation of the sandwich. If we use an ideal polar factor, its direction solves:

maximize⁡U ⟨M,U⟩subject to∥Dr−1UDc−1∥op≤1.\underset{U}{\operatorname{maximize}}\ \langle M,U\rangle \quad\text{subject to}\quad \left\|D_r^{-1}UD_c^{-1}\right\|_{\mathrm{op}}\leq 1.Umaximize​ ⟨M,U⟩subject to​Dr−1​UDc−1​​op​≤1.

Change variables to remove the two diagonal matrices from the constraint, and this becomes the ordinary polar-factor problem. Change back, and you get the same scaling on both sides of the polar transform.

The sandwich chooses a weighted geometry for the update: rows and columns with more old momentum get smaller coordinate allowances. The polar transform chooses a direction in that geometry; the final normalization sets its length.

Computing those row and column statistics is cheap on LoRA's skinny matrices. They're also available from the momentum we already have, so this construction needs no separate second-moment history or extra beta.

The final normalization also keeps the tall B factor from getting a much larger step just because of its shape. And the polar transform can spread the update across more of the factor's available singular directions.

LoRA adds a wrinkle here. Multiplying A by c and dividing B by c leaves BA unchanged, but changes the coordinates the optimizer sees. Equal-sized steps in A and B don't automatically mean equal-sized changes to the effective weight. The factors have their own geometry.

Part 2 The numerics rabbit hole#

Once we had the rule, we wanted to see the numbers line up. That led to questions about individual rounding steps, GPU kernels, and eventually a dot product that landed almost exactly between two BF16 values.

To reproduce the momentum cancellation tests, we needed FP32 for the current calculation and BF16 rounding for the state carried into the next step. Almost-canceling gradients make that distinction easy to see: the leftover tells you what survived rounding.

The polar computation#

Our spectral replay used five stages from the published Polar Express v3 coefficients, starting with:

X=round⁡FP16(DrMtDc1.01 max⁡(∥DrMtDc∥F,10−7)).X=\operatorname{round}_{\mathrm{FP16}}\left( \frac{D_rM_tD_c} {1.01\,\max(\|D_rM_tD_c\|_F,10^{-7})} \right).X=roundFP16​(1.01max(∥Dr​Mt​Dc​∥F​,10−7)Dr​Mt​Dc​​).

Then came the order of operations. For a tall matrix, let R = XᵀX. A polynomial stage can be written in Horner form:

X←X[aI+R(bI+cR)].X\leftarrow X\left[aI+R(bI+cR)\right].X←X[aI+R(bI+cR)].

The coefficients change each stage; wide matrices use the transposed construction. Most of the work happens on the small Gram matrix. Rounding the intermediates to FP16 makes this behave differently from an algebraically equivalent expanded expression.

We made tiny coordinates that would react strongly to rounding one particular intermediate. With the FP16 store, two new tests matched to around 2–4 × 10⁻⁸. Without it, their tiny-coordinate ratios missed by 19.8% and 4.6%.

Those errors barely showed up in a whole-vector norm. The small coordinates were useful precisely because they made an otherwise hidden rounding decision easy to see.

The rounding artifacts were fingerprints. We could choose an input that made two implementations disagree, then ask the API which answer it gave.

Moving the comparison onto a GPU#

One SST2 update still had a 0.79% spectral direction error on CPU. We were comparing CPU arithmetic with a service running on GPUs. Moving the comparison onto a GPU was overdue.

The same equations on an H100 brought that case down to about 7.7 × 10⁻⁸ error. All 2,913 mismatched inferred FP16 output values now matched.

The first Gram matrix had changed by one FP16 rounding step. The polynomial amplified it. No new optimizer term was needed to explain that case.

Even two local GPU paths disagreed. They used split-K multiplication, dividing dot products into groups and adding the partial results. One used 88 groups, the other 125. Reproducing those partitions with FP16 partial-result storage reproduced both paths throughout our B-factor tests.

The measuring instrument had quirks too#

There was another wrinkle: identical exported weights and matching selected log-probabilities didn't guarantee identical measured gradients. In one set of four measurements, three agreed and the fourth differed across all 253 B factors.

Small single-example probes exposed two accumulation behaviors. One rounded each contribution before combining it; the other combined the FP32 products before rounding:

BF16⁡ ⁣(BF16⁡(G1)−BF16⁡(G2))versusBF16⁡(G1−G2),\operatorname{BF16}\!\left(\operatorname{BF16}(G_1)-\operatorname{BF16}(G_2)\right) \quad\text{versus}\quad \operatorname{BF16}(G_1-G_2),BF16(BF16(G1​)−BF16(G2​))versusBF16(G1​−G2​),

For entries with unambiguous, nonzero source measurements, the second formula reproduced 12,068,664 values across all 253 modules with zero mismatches. A lot of numbers explained by a small change in where rounding happens.

LoRA gave us another useful trick here. At B = 0, a single-example B-gradient is approximately an outer product:

GB≈BF16⁡(δz⊤),z=sAh.G_B\approx\operatorname{BF16}(\delta z^\top), \qquad z=sAh.GB​≈BF16(δz⊤),z=sAh.

Each rounded gradient value constrains the projected activation z to an interval. Put enough of these constraints together and you can learn about a hidden activation without ever seeing it directly.

Changing A's random seed while keeping B zero gives you a second instrument measuring the same effective model. That caught us once: a hidden vector passed the first rank-eight projection and failed the second. Eight projected coordinates had hidden a difference in a 4,096-dimensional vector.

The last little mystery was one projection value sitting almost exactly on a BF16 rounding boundary. Because its operands were binary floats, we could calculate the dot product exactly with integer arithmetic. It landed about 1.24 × 10⁻⁷ below the midpoint.

It should round to −0.205078125. Our BF16 measurement GEMM returned −0.2041015625. Using the same operands with an FP32 or FP64 readout gave the expected answer.

With that readout change and contiguous base-weight storage, the projections from both instruments matched through six first-token transformer blocks and the next Q/K/V inputs.

We had spent time looking for a model difference when part of the problem was how we were measuring it.

Following the update through real data#

We replayed four steps of SST2 gradients through a local optimizer, using rank-one LoRA on Qwen3-8B's output projection. It carried its own momentum and weights while taking gradients measured at the hosted states. All recovered FP16 spectral output values matched, with relative update errors around 7 × 10⁻⁸ to 1.21 × 10⁻⁷.

There were still loose ends: a rank-two B continuation differed by 0.81%, and historical A updates by 1.14% RMS. We left those unexplained. Reproducing the entire training run, including the model's forward and backward passes, was a rabbit hole for another day.

What made this fun was finding ways to make a big, opaque system answer a small question.

A cold LoRA factor gave us a linear system. Learning rate zero let us change history without changing weights. Symmetry made the unknown polar response cancel. Tiny coordinates exposed rounding choices. A second projection checked whether the first one had missed something.

We started out curious about a LoRA optimizer and ended up calculating an exact dot product to settle an argument with a GPU. A good detour.
