Two NanoGPT experiments: attention gradients and table votes

Skipping some attention backward work, and letting an n-gram table vote on the answer.

November 7, 2026·4 min read
On this page
  1. How much attention needs a backward pass?
  2. Let the lookup table vote

I've been playing with modded-nanogpt, where the short track asks how quickly you can train a language model to a target validation loss. Two things I tried ended up being interesting for pretty different reasons: one cuts out work in attention's backward pass, and the other gives a lookup table a direct say in the model's predictions.

Both are open submissions: approximate backward and table voting. They build on different versions of the track, so their timings aren't directly comparable.

How much attention needs a backward pass?#

An attention head can look back over a long window, but it doesn't necessarily spread its attention evenly across that window. If most of the useful signal is concentrated nearby, maybe we can leave the forward pass alone and skip some distant work when calculating gradients.

That's what I tried in #371. For eligible heads, I compared backward windows of 64, 128, and 256 tokens with the original backward pass at two training steps. A head got the cheapest window whose query, key, and value gradients each had at most 0.2 relative L2 error on both steps and every rank. If none passed, it kept the full window.

The forward pass still sees the original window. In the backward pass, the kernel skips distant tiles while retaining the original softmax normalization; it doesn't renormalize the attention that remains. So this is a biased approximation, and attention being sharp isn't by itself a guarantee that the gradient will be close. The comparison against the actual gradients is what decides which heads get shortened.

The same submission also approximates the language-model head's weight gradient: it samples one row in four for the dense positive part and scales that contribution up, while accumulating the sparse target entries separately. The input gradient remains intact. Both approximations are used for part of training, and the last 87 updates use the original backward pass.

Together, on the same 8×H100 node, the modified run averaged 39.583 seconds over 12 runs versus 40.342 seconds over six baseline runs, with mean validation loss of 3.278705 versus 3.279000. That's a 1.88% time saving for the combined changes, including calibration. The comparison doesn't isolate how much each approximation contributed.

Let the lookup table vote#

The track has since taken a pretty dramatic turn. Herman Brunborg's #367 builds a huge, lossy n-gram lookup table on the CPU in parallel with training. It looks for matching contexts in training data and gives the transformer hints about what came next. In that submission, the table covers 37 billion tokens, and the reported training time drops from around 40 seconds to 6.7 seconds on the comparison machine.

That got me wondering how much of the table the network actually learns to use during such a short training run. The model gets the matches as input, but it still has to learn what to do with them. If it underuses a useful match, there's a very old-fashioned thing to try: count what followed that context and mix those counts directly into the answer.

In #399, the table gets a vote at validation. For the target token, the update is:

voted probability = (target count + k × network probability) / (total count + k)

Here k controls how much weight the network gets relative to the observed counts. A context with no match leaves the probability alone. I apply this successively for match lengths 6, 10, and 20, shortest first. The three weights were chosen once on a separate training shard that the table doesn't cover. There is no extra table, training, or backward pass for the vote.

On seven seeds, the network alone averaged 3.2933 validation loss; with the vote, it averaged 3.2737. The experiment used 526 training steps and a table covering 36.1 billion tokens, down from 540 steps and 37 billion in the reference setup. Since training and table construction run concurrently, that is roughly 2.5% less of each. These runs were on one H100, simulating the eight ranks in sequence, so that wall-clock saving is an estimate rather than a direct eight-GPU timing.

The result is consistent with the model leaving useful information in the table, though it doesn't prove exactly why the direct vote helps. I like that a smoothed n-gram count can still improve the final prediction even when the transformer has already seen the retrieval hints.
